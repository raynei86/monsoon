# Developer guide

This guide gives a high-level overview of the internal architecture and
algorithms used by Monsoon.

## Codebase layout

- `src/types.lisp` — core types, square and piece helpers, and bitboard
  constants.
- `src/position.lisp` — `position` struct and helpers for board state updates.
- `src/utils.lisp` — bitboard helpers and the iterate clause used by move
  generation.
- `src/moves.lisp` — move representation and move generation logic.
- `src/fen.lisp` — FEN parsing and `position-from-fen`.

## Core representation

Monsoon uses a bitboard-based representation. A `position` holds:

- 12 colored-piece bitboards (`pos-boards`): one per piece kind and color.
- 2 color bitboards (`pos-by-color`): aggregate by color.
- 6 piece bitboards (`pos-by-piece`): aggregate by piece kind.
- An occupancy bitboard that is always kept in sync.
- Side to move, castling rights, en passant square, and clocks.

State updates are done through `place-piece!` and `remove-piece!` so all
tracking bitboards stay consistent. `do-move` creates a copy of the
position, updates boards, and applies rule-specific effects (captures,
promotion, castling, en passant, clocks).

## Move generation overview

Move generation produces *pseudo-legal* moves and then filters with
`legal-move-p` using `king-in-check-p`.

### Precomputed attack tables

- `direction-to-offset` and `offsets` map compass directions to square deltas.
- `generate-attack-table` builds a 64-entry table by scanning each square and
  summing valid target bits for the provided directions and edge checks.
- `+king-attacks+` and `+knight-attacks+` are the resulting tables for jumping
  pieces, indexed by source square.
- Jumping piece move generation uses `generate-major-piece-moves` with
  `aref +knight-attacks+ from` or `aref +king-attacks+ from` to get attack
  masks, then splits captures and quiet moves by friendly/enemy masks.

### Rays and sliding pieces

- `generate-ray-table` builds rays for one direction, ignoring blockers.
  `+rays+` stores eight direction tables, and `ray` indexes into them.
- `ray-attacks` intersects a ray with occupied squares, then trims the ray at
  the first blocker using `lsb` or `msb` and `logxor`.
- `rook-attack-mask`, `bishop-attack-mask`, and `queen-attack-mask` are macros
  so they can use the anaphoric `from` bound by `generate-major-piece-moves`.
- Sliding piece move generation calls `generate-major-piece-moves` with the
  appropriate attack mask macro and relies on the same capture/quiet split.

### Pawns

- `with-pawn-params` binds push/capture shifts and ranks per side.
- `push1` and `push2` are quiet advances built by shifting the pawn bitboard and
  intersecting with empty squares.
- `cap-e` and `cap-w` shift only pawns not on the edge files, then intersect
  with enemy occupancy.
- Promotion targets are split from normal targets by the promotion rank and
  emitted with `emit-pawn-promos`.
- En passant uses the same capture shifts against a single ep-square bitboard
  and adds the en passant flag.

### Castling

Castling is generated by checking castling rights plus empty path masks. The
king move is emitted, and `do-move` relocates the rook based on flags.

## Check detection

`king-in-check-p` computes attacks against the king square by:

- Using pawn attack shifts from the king’s perspective.
- Using the knight and king attack tables.
- Using ray attacks for bishop/rook/queen sliders.

This avoids generating all opponent moves and keeps check detection local.
